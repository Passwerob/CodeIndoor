# SceneCode × aDSL 客厅场景生成 · 项目总览

> **定位**：把 SceneCode 的「场景组织 + 摆放」能力与 aDSL / FineScene 的「单件可编辑几何生成」能力打通，产出一个可交付、可溯源、自包含的客厅 3D 场景。
> **最后更新**：2026-11-09
> **当前状态**：✅ 布局闭环通过（硬约束 0 违规，15 件全部就位）；✅ 场景已在 Blender 落地并出图；🔶 视觉门禁的自动修复路由已写好，末次因上游限流未完成一轮视觉复验。

---

## 一、项目是什么

**SceneCode**（wangpuyi/SceneCode，论文 arXiv:2605.19587）是一套「可执行世界程序」系统，能为带铰接物体的室内场景生成可编辑场景。它本身是两层叠加：

- **A. 房间级 Agentic Backbone**：`floor_plan → furniture → wall_mounted → ceiling_mounted → manipuland` 五阶段，由 Planner 编排 Designer + Critic 迭代，文本 → 布局 → 逐物体摆放 → 渲染 → 评审 → 回滚。
- **B. 对象级 Code_Object 框架**：单个物体 → ObjectPlan → 逐部件 Blender Python 程序 → 执行/修复 → GLB/SDF/URDF。

**我们的目标**（用户原话）：*「我想要的是 SceneCode 的场景组织和摆放能力，结合我们调整好的 aDSL 的单个生成能力」*。

**分工契约**：

| | SceneCode 侧 | aDSL / FineScene 侧 |
|---|---|---|
| 职责 | 房间里有什么、分几阶段、放哪、朝向、彼此关系、动线、评审回灌 | 每件东西长什么样、可编辑部件层级、材质与几何 |
| 产物 | `layout.json` | 可编辑 aDSL 对象 + `.blend` |
| 禁止 | 产出任何几何 / bpy 代码 | 决定物体之间的空间关系 |

桥接层只做一件事：把 SceneCode 的 `placement{x,y,z,yaw_deg}` 通过 `apply_pose()` 盖到每个 aDSL 对象上，**没有新写任何几何**。

## 二、为什么做这轮改造（核心问题）

早期我交出的场景，Critic 只给 3–4 分，且大量问题（门洞偏移、电视没上墙、扶手椅朝向错、贴墙规则不落实）是我**在下游手工改坐标**补上的。用户一针见血地指出：

> 「这不还是不对么？我们本质上还是没有实现闭环啊？为什么要你写呢？本身不应该由整个的 agent 做么？之前就告诉你不要你自己动手改，你只能改 agent 的流程啊。SceneCode 本身摆放能力不行么？」

这四条硬约束定下了改造方向：

1. **不手工改产物**（坐标、位姿、几何）。
2. **只允许改 agent 的流程**（提示、约束、校验、反馈通道）。
3. **必须真闭环**——agent 自主决策并自我修复，而非我在下游补救。
4. 回答「SceneCode 摆放能力不行么」——定位能力缺口到底在哪。

我们定位到闭环断在 **4 处**：

1. Critic 判完就收工、无复验；
2. 约束里写死了过期数值（门洞坐标、扶手椅角度与下游不符）；
3. 场景门禁（视觉审查）给出的 `repair_target` 无人接，审查完就停；
4. 物件清单（inventory）写死 14 件，漏了 `wall_tv`、`entry_door`。

## 三、怎么把它变成真闭环（方法论）

围绕「让 agent 决策、代码只做确定性派生与校验」重构，六条原则写进了 `scene_layout.py` 的模块 docstring：

### 1. 单一事实源（single source of truth）
房间尺寸、墙面内表面、门窗洞口全部从装配后的壳体网格**实测**并发布成 `room_measured.json`，提示词、约束、装配三个阶段共用同一份数据，不再各写各的硬编码。
实测结果：室内净空 6.0 × 5.0 × 2.9 m；门洞 x 1.20~2.40（净 1.28~2.32，高 2.10）；窗 x −1.0~1.0、z 0.88~2.22。

### 2. 约束即测试（constraint as test）
`expect()` 返回带 id 的**类型化违规**（`walls.*`、`bounds`、`overlap.*`、`clearance.*`、`faces.*`、`in_front_of.*`、`above.*`、`centered.*`、`opening.window`…）。同一份违规列表同时用作：Designer 的反馈、Critic 的证据、循环的后置条件。约束不再写死数字，而是从实测派生。

### 3. 派生不决策（derive, don't decide）
凡是能由关系算出的分量，绝不交给模型拍脑袋：

- 吊灯 `z = 天花平面 − local_z`；挂画 `yaw = 墙面朝内法线`；
- 窗帘 `z` 由自身 local_z 反解使下摆落地；电视 `z = 柜顶 + 0.10 − local_z[0]`；
- 门扇 = 洞口 + 铰链偏移。

模型只控制 SceneCode 契约允许的 `x / y / yaw`，其余由 `resolve_pose()` 派生。

### 4. 暖启动增量修复（warm start）
上一轮已通过约束的位姿**直接保留**，只重排违反约束的物件。早期每轮全量重抽导致「修一件、推翻十一件」，越修越乱；暖启动后每轮只动该动的。

### 5. 依赖排序
`in_front_of` / `above` / `faces` / `centered_with` 指向的对象必须先于引用者放置，避免「沙发还没放，电视就先算朝向」的悬空问题。

### 6. 门禁 → 修复路由
`scene_gate_repair.py` 把视觉审查的 `findings` 按 `repair_target` 路由回责任阶段：`layout` 类回 Designer（逐个物件修，且只在本轮后所有硬约束仍通过才提交），其余（`decomposition`/`geometry`/`source`/`materials`/`camera`）作为工单报给对应阶段，绝不越权替别人修。

## 四、架构与模块

```
room_measured.json ─┐
assets_measured.json ┘→ scene_layout (Designer+Critic, 暖启动, 约束即测试)
                            ↓ layout.json  ──→ layout_finalize (派生门扇/定稿)
                                                 ↓ layout_finalized.json
                                          asset_supply (供给计划)
                                                 ↓ supply_plan.json
                          living_room.blend ──→ build_asset_scene (Blender 装配)
                                                 ↓
                                     _run_scene_gate (视觉门禁)
                                                 ↓ scene_visual_qa.json
                                       scene_gate_repair (路由回修)
                                                 ↓
                                          pack_delivery (打包交付)
```

| 模块 | 职责 |
|---|---|
| `room_spec.py` | 从壳体网格实测房间事实源，产出 `room_measured.json` |
| `measure_assets.py` | 在**根节点局部坐标**下测每件资产包围盒（纠正了 4 处手抄尺寸错误），产出 `assets_measured.json` |
| `scene_layout.py` | 闭环核心：Designer 逐个放置 + Critic + 暖启动 + 约束即测试 + 依赖排序 |
| `layout_finalize.py` | 从洞口派生门扇位姿，校验门扇与净洞口匹配（容差 60 mm），定稿 |
| `asset_supply.py` | 把布局翻译成资产供给计划 |
| `build_asset_scene.py` | Blender 装配：接管姿态、记录 drift、不擅自挪动任何物件 |
| `pack_delivery.py` | 清孤儿 → 合并同源贴图 → 全内嵌打包，产出自包含交付件 |
| `scene_gate_repair.py` | 视觉门禁 findings 按 `repair_target` 路由回责任阶段 |

## 五、关键结果（都已验证）

- **闭环通过**：`validation.passed = true`，`issues = []`，15 件物件全部就位（selected_round 1）。Critic 评分 7 / `needs_revision` 是**建议性**的审美意见，按设计不作为通过条件——硬约束才是关卡。
- **贴图打包**：直接 pack 758.1 MB → 清孤儿 346.4 MB → 合并同源 167.5 MB（120 张贴图），交付件 **零外部依赖**。三重校验（外链 0、链接库 0、内嵌图 `size≠0`）全过；合并后逐像素验证 max diff 4/255、平均亮度一致（133.62）。
- **可溯源**：场景的 7 件几何程序由 `deepseek-flash` 经本地兼容网关写（网关 49 次响应）；场景组织与布局由确定性代码完成；视觉验收由 `deepseek-flash` 经 FineScene 的 `general_vision` reviewer 完成。代码派生自模型响应，五项哈希全等才算通过。
- **场景已落地**：Blender 装配 13 件导入 + 2 件程序化（地毯/窗帘），0 报错，5 张出图。

## 六、怎么复现

前置：本地兼容网关 `bridge/gateway.py --port 8765`（把 SceneCode 模型名映射到 `deepseek-flash`，保证 `images.generate` 永不失败）；Blender 5.2。

```bash
# 1. 实测房间事实源 + 资产包围盒（产出 room_measured.json / assets_measured.json）
python -m adsl_adapter.room_spec
python -m adsl_adapter.measure_assets

# 2. 闭环布局（Designer+Critic+暖启动，产出 layout.json）
python -m adsl_adapter.scene_layout

# 3. 定稿（派生门扇，产出 layout_finalized.json）
python -m adsl_adapter.layout_finalize

# 4. 供给计划
python -m adsl_adapter.asset_supply

# 5. Blender 装配（接管姿态，不擅自挪动）
/e/Blender/blender.exe -b --python adsl_adapter/build_asset_scene.py

# 6. 视觉门禁
python -m adsl_adapter._run_scene_gate

# 7. 把审查 findings 路由回责任阶段修复
python -m adsl_adapter.scene_gate_repair

# 8. 打包交付（自包含 .blend）
python -m adsl_adapter.pack_delivery
```

> 注：`scene_layout` 依赖网关在线；上游限流（HTTP 429）时模块会记录并保留已成功的轮次，不会把整轮结果丢掉。
